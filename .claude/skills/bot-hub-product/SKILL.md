# Bot Hub Product Skill

## Product contract

The normal operator flow is always:

1. **Create** — name, purpose, optional description.
2. **Connect** — select a channel; use an official authorization handoff or instant Web Chat setup.
3. **Teach** — select AI / Scenario / Hybrid and add knowledge or a scenario template.
4. **Go Live** — validate minimum configuration and enable the bot.

Do not require an operator to understand webhook signatures, Router9 internals, model provider routing, raw n8n workflows or credential formats during this flow.

## Multi-bot boundaries

Every bot must keep its own `botId`, purpose, status, channels, knowledge, scenario and intelligence mode. Bot-aware webhook paths and workflow events must carry `botId`. Do not leak configuration between bots.

## QR connection rule

QR is a short-lived handoff URL generated by Bot Hub. It may open an approved OAuth/authorization flow, but it must never capture or persist personal social-network web sessions, QR-login cookies or browser credentials. Never mark an OAuth-dependent channel `connected` before the server-side provider authorization/token exchange has actually succeeded.

## Web UI direction

- Apple-inspired, not Apple-cloned.
- Strong type hierarchy, generous whitespace, restrained blur and neutral surfaces.
- Use color primarily for status and primary actions.
- Avoid dense SaaS dashboards and long first-level navigation.
- Keep first-level navigation product-oriented.
- Prefer inline progressive disclosure over configuration walls.
- Mobile keeps the primary product areas accessible without reproducing desktop navigation verbatim.

## Quality gate

After changes:

```bash
npm run check
npm test
```

For onboarding/API changes, keep an end-to-end test for Create → Connect → Teach → Go Live → Simulate. For QR changes, keep deterministic QR matrix/SVG tests and preserve the short-lived session contract.
